Admin UI

[0022]

The dashboard ships inside the binary.

The admin app is plain HTML, CSS and JavaScript, baked in at compile time with include_str!. rpocketbase serve needs no frontend build and no second server. The script files are joined in a fixed order into one scope, without a bundler.

Covers

20

Realtime (SSE)

[0020]

One long-lived request, fanned out in process.

A client opens a single request to the realtime endpoint and keeps it open. The first message gives it a clientId, and record changes stream in after that. The hub that fans events out lives inside the process. That keeps it simple and fast, and it also makes rPocketBase a single instance, not a cluster.

GET /api/realtime
event: PB_CONNECT
data: {"clientId": "…"}
Keep-alive
Every 15 seconds
Auth
Browsers' EventSource can't set headers, so it sends ?token=
API keys
A key's collection allowlist applies to events too
Scale
One instance: the hub and the rate limits live in memory
18

REST API

[0018]

PocketBase-shaped, on purpose.

Every collection's records live at one predictable address. Filtering, sorting and paging are query parameters, written in the same expression language as the rules below. Files are served with short-lived tickets, so a session token never ends up in a URL.

GET /api/collections/tasks/records?filter=(status='open')&sort=-created
Records
/api/collections/{name}/records
One record
…/records/{id}. There is no /record/.
Files
/api/files/{collection}/{id}/{file}
Tickets
rpbf_<expiry>_<hmac-sha256>
Caching
API responses are never cached
Health
/api/health reports liveness and version only
16

Auth

[0016]

Slow to guess, fast to check.

Passwords are hashed with Argon2id. A login for an email that doesn't exist still runs a full Argon2 check against a dummy hash, so the response time doesn't reveal which accounts exist. Sessions are signed tokens with hard limits, and machine keys never get superuser powers.

$argon2id$v=19$m=19456,t=2,p=1$…
Hash
Argon2id, 19 MiB of memory, 2 passes, 1 lane
Sessions
HS256 JWT, valid 24 hours; renewable for up to 7 days from sign-in
Limits
20 failed logins per 15 min per email, 40 per IP, then HTTP 429
API keys
rpbk_…, never superusers: the collection allowlist is checked first, then the normal rules
Compare
Constant-time for keys and token digests
First run
The installer locks after the first superuser is created
14

Rules engine

[0014]

Every rule becomes SQL, or nothing.

Each collection has list, view, create, update and delete rules, written in a PocketBase-compatible expression language. List rules compile to parameterized SQL. If a rule can't be compiled, the query becomes WHERE 1 = 0: you get an empty list, never an unfiltered one.

listRule  owner = @request.auth.id && status != "archived"
Null rule
Superusers only
Empty rule
Public
Operators
= != > >= < <= ~ !~, plus ? any-of forms
Context
@request.auth.* @request.body.* @now …
Modifiers
:isset :changed :length :lower
Guardrail
Client filters can't reference @collection, password or tokenKey
12

Schema

[0012]

Collections are tables. Fields are columns. Views are queries.

A collection is the unit of schema. Creating one creates a SQLite table below; each field adds a column. A collection can also carry behavior packs, such as append-only, soft delete and TTL expiry. The whole schema travels as JSON, and an import is checked in full before anything is written, so a bad entry late in the file can't leave half a schema behind.

Kinds
Base collections, auth collections, and views
Portable
Export and import the schema as JSON
Behaviors
Append-only, soft delete, TTL expiry

12bSecret fields

One of the fourteen types is sealed. What lands in SQLite is an AES-256-GCM envelope, not plain text. It unlocks with the server key or with a passphrase (stretched with Argon2id), and only through an explicit reveal request, which can be audited.

POST /api/collections/{name}/records/{id}/reveal
Cipher
AES-256-GCM
Keys
The server key (.vault_key) or a passphrase stretched with Argon2id
Reveal
A dedicated endpoint, with configurable audit destinations
Caution
Backups include .vault_key

12cViews

A view is a collection with a query instead of columns. Before it is created, the query has to prove it only reads: write keywords are rejected, and a column policy blocks password and tokenKey from being selected out under another name. The fields are then read back from the database rather than declared, so the view's shape always matches what the query actually returns.

viewQuery  SELECT id, owner, COUNT(*) AS runs FROM jobs GROUP BY owner
Runs where
It becomes a real SQLite view, so the query runs in layer 10 on every read
Columns
Read back from the database, not declared by hand
Rules
listRule and viewRule apply as they do anywhere else
Writes
Refused: "View collections are read-only."
Admin
The view builder previews columns and sample rows before you save
10

SQLite

[0010]

One file, written ahead.

Data lives in an embedded SQLite database in pb_data, opened in write-ahead-log (WAL) mode so reads don't wait on writes. Views are real SQLite views, checked to be read-only before they're created. Uploaded files sit next to the database in pb_data/storage.

Journal
WAL
Integrity
Foreign keys on; 5,000 ms busy timeout
Views
Read-only viewQuery, with columns read back from the database
Expiry
Collection-level TTL, plus a sweep an admin can run
Backups
A zip of the database, WAL, file storage and secrets. Treat it as secret.

One binary

[0100]

Everything above is one process.

rpocketbase serve starts all seven layers from a single Rust binary: no Node, no separate frontend, no external database. If you want TLS, put Caddy in front of it. Caddy is the one piece that runs outside the binary.

$ rpocketbase serve
rPocketBase listening on 127.0.0.1:8090
